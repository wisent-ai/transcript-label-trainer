Existing-data onboarding

Import an existing labeled corpus

Use the CLI with a filesystem path or upload the same canonical bundle in the local browser workspace. Both surfaces call the same Rust adoption engine and produce the same retained corpus identity and counts.

Launch the graphical importer

transcript-label-trainer gui

The command binds an available port on 127.0.0.1, prints a session-specific URL, and waits. It deliberately does not open a browser. Copy the printed Corpus importer URL into a modern local browser. The URL fragment carries a random session token; the frontend moves it into tab-scoped session storage before calling the API.

Choose roots before the command name. An explicit port is optional:

transcript-label-trainer \
  --training-root /srv/wisent/trainer \
  --storage-root /srv/wisent/lake \
  gui --bind 127.0.0.1 --port 8765
--bind IP
Listener IP. Default: 127.0.0.1. Only loopback IP literals are accepted; ::1 is also supported.
--port PORT
Listener port from 0 through 65535. Default: 0, which asks the operating system for an available port.
--training-root PATH
Global flag controlling the model and adopted-corpus root. It overrides $TLT_HOME and Stado placement and must precede gui.
--storage-root PATH
Global flag selecting the read-only lake root. It overrides $LAKE_DATA and Stado placement and must precede gui. Corpus adoption does not write there.

The workspace shows both resolved roots, accepts a real local file through the browser file picker, displays imported/unchanged/conflicting/rejected counts, and reads <training root>/corpora/registry.json back after adoption. Refresh performs another persisted-state read; it does not infer success from the chosen filename.

Import from the CLI

transcript-label-trainer \
  --training-root /srv/wisent/trainer \
  corpus-adopt /absolute/path/dataset-bundle.json

transcript-label-trainer \
  --training-root /srv/wisent/trainer \
  corpus-status --json

corpus-adopt BUNDLE [--json] canonicalizes the source path, validates the complete file before mutation, retains the canonical bytes, and selects the corpus. corpus-status [--json] reads the registry and reports the selected entry plus every retained entry. The onboarding journey's --corpus BUNDLE option calls this same path-based operation.

Canonical dataset-bundle schema

The JSON object has exactly three top-level fields. Unknown fields are refused.

{
  "schema_version": 1,
  "aspect": "reviewed",
  "labels": [
    {
      "session_id": "native-session-id",
      "value": "yes",
      "source": "manual",
      "ts": "2026-09-05T12:00:00Z",
      "runtime": "omp",
      "text": "Reconstructed user and assistant transcript text"
    }
  ]
}

schema_version must be 1. aspect must be a safe trainer aspect name. labels must be nonempty. Every row requires nonblank session_id, value, source, and text; ts must be RFC 3339; runtime is either a nonblank string or null. A native session ID may occur only once in a bundle.

Identity, selection, and result counts

The engine serializes the validated bundle canonically and hashes those bytes with SHA-256. Its durable identity is dataset-bundle:<sha256>, and its retained file is <training root>/corpora/<sha256>.json. This is the training input selected by later explicit train, infer, and evaluate commands.

A CLI source identity is its canonical absolute path. A browser source identity is browser-upload:sha256:<raw-upload-sha256>; it is stable without staging the uploaded bytes in /tmp or another transient file. The original browser basename is retained separately for display. The corpus identity remains canonical-content based, so it is independent of the transport.

Imported
Records in a valid canonical corpus whose content-addressed file was newly retained.
Unchanged
Records in an identical corpus already retained. The operation is idempotent and selects that corpus again.
Conflicting
An existing file at the computed identity path did not contain the canonical bytes. The engine refuses to overwrite it and changes no registry state.
Rejected
The complete upload was refused before selection. The GUI reports one rejected source; the diagnostic identifies the first violated contract.

A different valid corpus never overwrites the prior corpus. Both remain in the registry, and the newly imported identity becomes selected. There is no merge, per-row overwrite, or drop-invalid-rows mode.

Refusals and diagnostics

invalid dataset bundle …; no corpus state was changed
The upload is not valid JSON or does not match the exact schema and field types.
unsupported dataset bundle schema …; expected 1
The top-level schema_version is not supported by this binary.
invalid aspect name '…': use lowercase letters, digits, '-' and '_'
The aspect is empty, starts with punctuation or an uppercase letter, or contains a character that cannot safely name a trainer artifact directory.
dataset bundle … contains no label records
The labels array is empty.
requires nonempty session_id, value, source, and text
At least one required row value is empty or whitespace.
has invalid RFC 3339 ts
A row timestamp cannot be parsed as RFC 3339.
has an empty runtime; use null when unknown
An optional runtime was supplied as an empty string rather than null.
repeats native session_id …
Two rows claim the same native session identity. The whole file is refused.
corpus identity conflict …; no corpus state was changed
The content-addressed retained file was modified or replaced. Restore or investigate the retained store; the importer will not overwrite evidence.
could not resolve corpus … / corpus is not a regular file
The CLI source path is missing, inaccessible, or does not identify a file.
invalid corpus registry … / unsupported corpus registry schema … / selects unknown corpus …
The persisted registry cannot be trusted or understood. Adoption and status refuse rather than replacing it.
corpus upload must contain 1-16777216 bytes
The GUI rejected an empty or oversized request before parsing JSON. CLI reads are bounded only by the filesystem and available memory.
uploaded corpus filename must be a 1-255 character basename
The browser-supplied name is empty, too long, a path, or contains control characters.

Runtime, security, and side effects

The installed binary contains the HTML, JavaScript, CSS, and these documentation pages; no source checkout or asset server is needed at runtime. Installation requires Rust 1.85 or newer. Running the GUI requires only the installed binary, a local browser, and read/write access to the selected training root. A lake installation is not required to adopt or inspect a corpus, and the storage root is not changed.

No model side effects: importing a corpus does not run train, run, evaluate, infer, teacher/judge calls, or Stado fleet work. Those remain separate commands.

The host only accepts loopback IP listeners and loopback clients. Every request must carry the listener's exact Host; API calls require the random session token; mutation also requires the exact listener Origin. This rejects cross-origin submission and DNS rebinding. Upload length is checked before the JSON parser. Responses carry a restrictive Content Security Policy, untrusted values are inserted as text rather than HTML, and no permissive CORS headers are emitted.
